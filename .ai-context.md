### Phase 1: Docker Infrastructure (Complete ✅)

### Phase 2: Learning Mode (Complete ✅)
**Problem:** Adding new languages was time-consuming (hours of manual work)  
**Solution:** Interactive tool to create locales in 10 minutes:
- Automatic UI label collection via JavaScript
- Terminal-based interactive mapping
- YAML generation for new locales
- Validation tools

**Key Files:**
- `learning.go` (~500 lines) - Main implementation

**How It Works:**
```
Login → Collect Labels → Interactive Mapping → Generate YAML
```

User runs: `make learn` or `gphotos-cdp -learn`

## 🛠️ Technical Architecture

### Docker Setup
```
┌─────────────────────────┐
│  Multi-stage Build      │
├─────────────────────────┤
│ 1. Builder (golang:1.23)│
│    - Compile Go code     │
│    - Include learning.go │
│                          │
│ 2. Runtime (debian-slim) │
│    - Chromium headless   │
│    - Non-root user       │
│    - Health checks       │
└─────────────────────────┘
```

### Learning Mode Flow
```
User: make learn
  ↓
Docker: Run with -it (interactive terminal)
  ↓
learning.go: Launch Chrome headless
  ↓
Navigate to Google Photos
  ↓
Execute JavaScript collectors
  ↓
Present numbered list to user
  ↓
User selects mappings (terminal input)
  ↓
Generate GPhotosLocale struct
  ↓
Marshal to YAML
  ↓
Save to locales-XX.yaml
```

### Locale Structure

## 🔍 Key Decisions & Rationale

### Why Docker-First?
- Easier deployment on headless servers
- Consistent environment
- No OS-specific dependencies
- Chrome + dependencies bundled

### Why Learning Mode?
- Dramatic time savings: Hours → 10 minutes
- Lowers barrier for locale contributions
- No manual DOM inspection needed
- JSON data automatically collected

### Why Multi-Arch?
- Support ARM servers (Raspberry Pi, cloud ARM)
- Future-proofing
- Wider hardware compatibility

### Why Extensive Documentation?
- Self-service user support
- Easier onboarding
- Community contributions
- Knowledge preservation
